## 1. FastAPI 分层与依赖注入

### 1.1 分层职责

```text
api/          路由与 HTTP 参数
core/         配置、日志、异常、加密、限流
db/           连接、建表、初始化
models/       SQLAlchemy 实体
schemas/      Pydantic 请求/响应模型
services/     业务编排
repositories/ 数据库操作
adapters/     外部模型适配（LiteLLM）
utils/        工具
```

核心思想：**路由不写业务、服务不写 SQL、仓库不写 HTTP**。每层只依赖下一层，方便单测与替换。

### 1.2 FastAPI 依赖注入

```python
def get_db():
    db = SessionLocal()
    try:
        yield db
    finally:
        db.close()

@router.get("/sessions")
def list_sessions(user: User = Depends(get_current_user), db: Session = Depends(get_db)):
    return ok({"sessions": session_service.list_sessions(db, user.id)})
```

- `Depends(get_db)`：每个请求一个数据库会话，结束自动关闭。
- `Depends(get_current_user)`：从 Bearer Token 解析当前用户。
- 依赖可以嵌套：`get_current_user` 内部又依赖 `get_db`。

### 1.3 面试追问

问：依赖注入解决了什么问题？

答：解决“对象创建与生命周期管理”的耦合。测试时可以用 `app.dependency_overrides` 替换数据库或当前用户，业务代码不用改。

问：为什么 FastAPI 能区分 query/body/header？

答：FastAPI 根据类型与默认值推断：Pydantic 模型是 body，`Depends` 是依赖，`Header`/`Query` 显式声明参数位置。

## 2. SQLAlchemy 与数据库设计

### 2.1 实体关系

```text
User 1 ──── * ChatSession 1 ──── * ChatMessage
User 1 ──── * Document
User 1 ──── * RefreshToken
User 1 ──── * ModelCall
```

```python
class ChatSession(Base):
    __tablename__ = "chat_sessions"
    user_id = mapped_column(ForeignKey("users.id", ondelete="CASCADE"), index=True)
    messages = relationship(back_populates="session", cascade="all, delete-orphan")
```

### 2.2 级联删除

两层保障：

- 数据库外键 `ondelete="CASCADE"`：删用户时数据库删会话。
- ORM `cascade="all, delete-orphan"`：删会话时 ORM 先删消息。

面试点：**为什么两层都要？** SQLite 默认不启用外键，ORM 层删除保证测试与生产行为一致；生产靠数据库兜底。

### 2.3 事务边界

服务层通常这样写：

```python
db.add(message)
touch_session(db, session_id)
db.commit()
```

`commit` 前失败会回滚，保证“消息与会话更新时间”原子。

### 2.4 create_all 的问题

`Base.metadata.create_all` 只建新表，不能改旧表结构。生产需要 Alembic（阶段 12 规划）。面试时主动说出这个局限，体现工程判断。

### 2.5 面试追问

问：为什么删除会话要 cascade 而不手动删？

答：避免漏删产生孤儿数据；声明式关系让意图清晰。

问：外键要不要加索引？

答：凡是按外键查询（如按 user_id 查会话）都要加索引，否则全表扫描。

## 3. 加密与认证安全

### 3.1 Fernet 加密（API Key）

```python
def encrypt_secret(value):
    return Fernet(secret_key).encrypt(value.encode()).decode()
```

为什么 API Key 用加密不是哈希？调用模型时需要解密还原，属于可逆数据；密码用 bcrypt 是因为只需要校验，不可逆。

### 3.2 bcrypt

```python
hash = bcrypt.hashpw(password.encode(), bcrypt.gensalt())
bcrypt.checkpw(password.encode(), stored_hash)
```

特点：

- 自动加盐，相同密码不同哈希
- 慢哈希，提高撞库成本
- `checkpw` 遇到非法哈希要捕获 `ValueError`

### 3.3 JWT

```python
payload = {"sub": str(user_id), "exp": now + timedelta(minutes=60)}
token = jwt.encode(payload, jwt_secret, algorithm="HS256")
```

特点：

- 无状态：服务端不用存 session，验签即可
- 只能撤销“签发前”的 token？不，JWT 本身难撤销，所以用短有效期 + refresh
- 生产密钥必须 >= 32 字节，否则 `InsecureKeyLengthWarning`

### 3.4 刷新令牌轮换

```text
login → refresh_token 原文给前端，数据库存 SHA-256 哈希
refresh → 校验哈希/未撤销/未过期 → 撤销旧记录 → 生成新令牌对
logout → 标记 revoked
```

为什么存哈希：

- 数据库泄露后攻击者拿不到原文
- SHA-256 足够，因为 refresh token 本身就是高熵随机串

为什么轮换：

- 旧 token 即使被偷，刷新一次后失效
- 发现“旧 token 还能刷新”可作为被盗检测信号

### 3.5 面试追问

问：JWT 被偷怎么办？

答：短期 access + 可撤销 refresh；生产建议 HttpOnly Cookie 降低 XSS 面。

问：为什么不用 Session？

答：JWT 适合前后端分离与多服务共享；Session 需要服务端存储，撤销方便但扩展要共享存储。

## 4. SSE 与流式输出

### 4.1 SSE 协议

```text
HTTP/1.1 200 OK
Content-Type: text/event-stream

data: {"type":"delta","content":"你好"}

data: {"type":"done","usage":null}

```

特点：

- 服务端单向推送
- 走普通 HTTP，Nginx 也能代理（要关缓冲）
- 浏览器原生 `EventSource` 只支持 GET，所以本项目用 `fetch + ReadableStream`

### 4.2 后端事件流

```python
async def event_stream():
    async for event in stream_chat_events(...):
        yield f"data: {json.dumps(event, ensure_ascii=False)}\n\n"
```

`finally` 里做消息持久化、记忆写入、模型统计，保证异常也收尾。

### 4.3 前端解析

```ts
const reader = resp.body.getReader()
const decoder = new TextDecoder('utf-8')
let buffer = ''
while (true) {
  const { done, value } = await reader.read()
  if (done) break
  buffer += decoder.decode(value, { stream: true })
  const parts = buffer.split('\n\n')
  buffer = parts.pop() ?? ''
  for (const part of parts) {
    const line = part.split('\n').find(l => l.startsWith('data: '))
    if (line) handleEvent(JSON.parse(line.slice(6)))
  }
}
```

为什么保留 buffer：网络分块可能把一个事件拆成两段，必须等空行才能判定事件完整。

### 4.4 打字机与 Vue 响应式

```ts
// 错误写法：修改 push 前的原始对象，Vue 追踪不到
const aiMsg = { role: 'assistant', content: '' }
session.messages.push(aiMsg)
aiMsg.content += delta   // 页面不更新

// 正确写法：push 后从数组取响应式代理
session.messages.push({ role: 'assistant', content: '' })
const aiMsg = session.messages[session.messages.length - 1]
aiMsg.content += delta   // 触发更新
```

打字机实现：

```ts
let pending = ''
let timer: number | undefined
onDelta: (delta) => {
  pending += delta
  startReveal()
}
// 每 20ms 显示 2 个字符
timer = setInterval(() => {
  aiMsg.content += pending.slice(0, 2)
  pending = pending.slice(2)
}, 20)
```

流结束 `flushTypewriter()` 立即补全，防止丢内容。

### 4.5 面试追问

问：为什么 Nginx 代理后打字机失效？

答：默认 `proxy_buffering on` 会等整个响应再发给客户端；SSE 必须 `proxy_buffering off`。

问：断流怎么办？

答：未输出内容时后端自动重试；已输出内容不重试，前端提示用户重发。

## 5. RAG 深挖

### 5.1 全链路

```text
解析 → 切片 → Embedding → Qdrant 入库
问题 → Embedding → 检索 → RAG Prompt → 模型回答
```

### 5.2 切片原理

```python
def split_text(text, chunk_size=500, chunk_overlap=50):
    step = max(1, chunk_size - chunk_overlap)
    ...
```

为什么重叠：如果关键句跨片段，无重叠会两半都不完整。

面试扩展：生产常用“先按段落/句子切，再合并到目标长度”，固定窗口只是入门实现。

### 5.3 Embedding

- `BAAI/bge-m3`：1024 维，多语言，中英检索质量好
- `embedding-2`（智谱）当时账号无额度，退回本地哈希向量做开发兜底
- 本地哈希向量是“字符二元组哈希”，只演示链路，不谈语义

面试点：**向量维度必须与 Qdrant 集合一致**；启动时 `ensure_collections` 发现维度不匹配会重建集合。

### 5.4 Qdrant 内部

```python
PointStruct(
    id=uuid5(...),
    vector=vector,
    payload={"doc_id": ..., "user_id": ..., "text": ..., "chunk_index": ...},
)
client.search(
    collection_name="document_vectors",
    query_vector=vector,
    query_filter=Filter(must=[FieldCondition(key="user_id", match=MatchValue(value=user_id))]),
    limit=top_k,
    score_threshold=threshold,
)
```

- 点 ID 用 UUID：字符串 ID 必须是合法 UUID，否则 Qdrant 拒绝
- payload 存原文：检索命中后直接拿文本拼 Prompt，不用二次查 PG
- Filter：按用户隔离，防止检索串数据

### 5.5 相似度

Cosine 相似度：

```text
cos(a,b) = (a·b) / (|a|·|b|)
```

越接近 1 越相关。`score_threshold` 过滤低相关片段。

### 5.6 RAG Prompt

```text
[system] 请只依据以下资料回答，资料不足时如实说明：
[片段1] ...
[片段2] ...

[user] 问题
```

为什么强调“只依据资料”：显著减少模型“脑补”。

### 5.7 RAG 局限与改进

局限：

- 纯向量检索对专有名词/ID 不友好
- TopK 片段可能互相冲突
- 没有答案来源可验证

改进（规划中，面试可讲思路）：

- 混合检索：BM25 关键词 + 向量 + RRF 融合
- Rerank：`bge-reranker` 精排
- 引用溯源：返回 `doc_id/chunk_index`
- 查询改写 / HyDE

### 5.8 面试追问

问：怎么评估 RAG 好坏？

答：检索侧看 Recall@K、MRR；生成侧看答案准确率、引用率、幻觉率；可做小测试集人工打分。

问：阈值为什么是 0.35？

答：默认值，需要看真实 score 分布调，不同 Embedding/领域差异很大。

## 6. 长期向量记忆

### 6.1 写入

```text
每轮结束：
记忆文本 = "用户：...\nAI：..."
向量化 → upsert memory_vectors
payload: user_id/session_id/text/type=memory
```

### 6.2 召回

```text
问题向量化 → search memory_vectors
  filter: user_id = 当前用户
  must_not: session_id = 当前会话
  top_k, threshold
```

为什么排除当前会话：当前会话上下文已经作为短期记忆给模型，避免重复。

### 6.3 融合

```text
最终 Prompt = 历史记忆 + 知识库片段（可选） + 当前上下文 + 新问题
```

### 6.4 面试追问

问：长期记忆和 RAG 有什么区别？

答：RAG 存文档，回答“知识型问题”；记忆存“你是谁/以前说过什么”，回答“个性化上下文”。两者可以融合。

问：记忆越积越多怎么办？

答：需要画像抽取、去重、过期、编辑（规划中）。

## 7. Agent / Function Calling

### 7.1 协议消息

模型请求工具：

```json
{
  "role": "assistant",
  "content": null,
  "tool_calls": [
    {"id": "call_1", "type": "function", "function": {"name": "calculator", "arguments": "{\"expression\":\"2+3*4\"}"}}
  ]
}
```

工具结果：

```json
{"role": "tool", "tool_call_id": "call_1", "content": "2+3*4 = 14"}
```

### 7.2 Agent 循环

```text
for _ in range(max_tool_rounds):
    resp = chat(messages, tools=list_tools())
    if not resp.tool_calls:
        return resp.content
    append assistant tool_calls message
    for tc in resp.tool_calls:
        execute → append tool message
```

### 7.3 安全

- 计算器用 AST 白名单，禁止 `eval`
- 工具参数 JSON 解析失败要兜底
- 用户数据工具必须带 user_id
- 外部 API 超时 8s，失败返回友好提示

### 7.4 面试追问

问：Function Calling 和“让模型输出 JSON 再解析”区别？

答：Function Calling 是模型原生能力，结构稳定、支持多工具调用；JSON 解析容易格式错误。

问：Agent 循环为什么最多 3 轮？

答：防止死循环、控制成本；真实场景一般 1-2 轮就够。

## 8. 工程化

### 8.1 限流：滑动窗口

```text
每个 IP 维护时间戳列表
过滤窗口外的旧记录
数量 >= limit → 429
否则追加当前时间
```

为什么滑动窗口比固定窗口好：固定窗口在边界会有“两倍突发”，滑动窗口平滑。

局限：单机内存实现，多实例需要 Redis（规划中）。

### 8.2 流式重试

```text
未输出任何 delta → 重试
已输出过 delta → 不再重试
```

为什么已输出不重试：重试会重复文本，用户看到一半又从头来。

### 8.3 调用统计

`model_calls` 表：

```text
model / session_id / success / token_count(估算) / duration_ms
```

`GET /api/stats` 聚合总次数、成功率、Token、按模型。

为什么 Token 是估算：模型 usage 有时拿不到或不准，先用 `len(text)//2` 估算。

### 8.4 日志观测

```text
FastAPI stdout
  → Promtail 通过 docker.sock 尾随容器日志
  → Loki 存储索引
  → Grafana Live Tail
```

关键点：

- 日志走 stdout，不写文件，容器天然采集
- ASGI 中间件记录 request start/body/end
- SSE 逐段 delta 日志方便排查“卡在哪一段”

### 8.5 Docker / Nginx

- 前端多阶段构建：Node 构建 + Nginx 运行
- Nginx `/api` 代理到 backend，`proxy_buffering off` 保证 SSE
- SPA `try_files ... /index.html`
- backend/frontend healthcheck
- `docker-compose.yml` 用 `include` 合并观测栈与工具

### 8.6 面试追问

问：为什么日志不直接写文件？

答：容器 stdout 由 Docker 统一采集，Promtail/Loki 天然集成，还便于 `docker logs`。

问：怎么排查 SSE 卡住？

答：看 Loki 里 `chat_stream delta` 是否连续、`request end` 是否出现；再用 duration 对比模型耗时。

## 9. 多租户隔离

原则：

- 所有业务查询/写入显式带 `user_id`
- 越权访问返回 404，不返回 403，避免暴露资源存在
- 向量 payload 也带 `user_id`，Qdrant Filter 过滤
- 刷新令牌、模型调用统计等按用户维度或全局隔离要有明确决策

本项目决策：

- 会话/消息/文档/记忆：用户隔离
- stats 与模型配置：暂全局（阶段 12 再细化）

面试追问：如果 Qdrant 没过滤 user_id 会怎样？

答：A 用户能检索到 B 用户的文档/记忆，属于越权漏洞；所以检索 Filter 必须带 user_id。

## 10. 前端要点

### 10.1 axios vs fetch

- axios：拦截器统一加 Token、处理 401、统一错误提示
- SSE 聊天用 fetch：因为要读流
- **坑**：fetch 不走 axios 拦截器，必须自己加 Authorization，否则 401

### 10.2 路由守卫

```ts
router.beforeEach((to) => {
  const token = localStorage.getItem('access_token')
  if (to.path !== '/login' && !token) return { path: '/login' }
  return true
})
```

### 10.3 布局交互

- 聊天输入框固定底部，消息区独立滚动
- 回底按钮：距底部 > 160px 显示，点击平滑回底
- `prefers-reduced-motion` 时关闭动画
