# 阶段零：环境搭建与架构初始化 · 原始需求

**需求来源：** [AIGC对话+RAG+AI记忆项目 全阶段落地开发手册（零基础练手版）](../../../../../../AIGC对话+RAG+AI记忆项目 全阶段落地开发手册（零基础练手版）.md)

**模块类型：** feature
**目标版本：** v1.0.0
**需求日期：** 2026-08-12

## 1. 需求背景

这是一个从零搭建的个人 AIGC 练手项目，最终目标是一个 AI 网页对话平台，支持：

- 多 AI 大模型统一对接（官方 Key + 中转 Key 可切换）
- 自研完整 RAG 链路（文档知识库问答）
- 双层 AI 记忆（短期会话记忆 + 长期向量记忆）
- 流式聊天、历史会话管理、Docker 容器化部署

阶段零是整个项目的地基，只做**环境统一与架构骨架**，不实现业务功能，保证后续 1～6 阶段在稳定、清晰、可扩展的基础上开发。

## 2. 阶段目标

1. 统一本地开发环境，固定技术栈版本。
2. 搭建 FastAPI 后端分层架构，预留模型适配、配置管理、异常处理能力。
3. 通过 Docker 部署 PostgreSQL 与 Qdrant，并验证连通性。
4. 初始化 Vue3 + TypeScript 前端，配置路由、全局请求与 UI 组件库。
5. 建立统一的多环境配置文件与项目规范，杜绝密钥硬编码。

## 4. 技术栈与版本约束

| 层次 | 技术 | 约束/说明 |
|------|------|-----------|
| 后端 | Python 3.11+ / FastAPI / Uvicorn | 使用异步模式 |
| 模型层 | LiteLLM | 阶段 0 仅安装依赖并封装占位适配器，不裸调模型 |

| UI | Element Plus | 全量引入或按需引入，二选一后固定 |

## 5. 详细任务分解

### 5.1 后端基础搭建（S0-01）

- 初始化 FastAPI 项目目录，采用分层结构：

  ```text
  backend/
  ├── app/
  │   ├── api/          # 路由层（接口入口）
  │   ├── core/         # 配置、日志、异常、安全
  │   ├── models/       # SQLAlchemy 模型（阶段 2 使用）
  │   ├── schemas/      # Pydantic 入参/出参
  │   ├── services/     # 服务层（业务逻辑）
  │   ├── adapters/     # 模型适配层（LiteLLM 二次封装占位）
  │   ├── repositories/ # 数据访问层（阶段 2 使用）
  │   └── utils/        # 工具层
  ├── tests/            # 基础测试
  ├── .env.example
  └── requirements.txt / pyproject.toml
  ```

- 安装核心依赖：fastapi、uvicorn[standard]、litellm、sqlalchemy、psycopg[binary]、pydantic、pydantic-settings、python-dotenv、cryptography、python-multipart。
- 提供 `GET /api/health` 健康检查接口，返回服务状态与时间。
- 统一响应格式：`{ code, message, data }`，统一异常处理中间件。
- 预留 `app/adapters/model_adapter.py` 占位文件，定义统一入参/出参协议（阶段 1 实现）。

### 5.2 数据库环境搭建（S0-02）

- 编写 `docker-compose.yml`，部署 PostgreSQL 16：
  - 项目专属数据库：`aigc_chat`
  - 独立用户与密码，禁止使用默认 postgres 弱口令
  - 数据目录挂载 volume，端口不与其他项目冲突
- 配置 SQLAlchemy engine 与 session，支持从环境变量读取连接串。
- 编写数据库连通测试：启动后能成功建立连接、执行 `SELECT 1`。
- 不创建业务表；表结构属于阶段 2。

### 5.3 向量库环境搭建（S0-03）

- 在 `docker-compose.yml` 中追加 Qdrant 服务。
- 启动后通过 REST/HTTP 或 qdrant-client 验证连通性。
- 创建两个专属 Collection：
  - `document_vectors`：存储文档知识库向量（阶段 3）
  - `memory_vectors`：存储长期记忆向量（阶段 4）
- Collection 向量维度与距离度量在配置中预留（阶段 3/4 确定实际值）。
- 不实现任何入库/检索业务逻辑。

### 5.4 前端基础搭建（S0-04）

- 初始化 Vue3 + TypeScript + Vite 工程，目录结构：

  ```text
  frontend/
  ├── src/
  │   ├── api/          # 接口请求封装
  │   ├── router/       # 路由
  │   ├── layouts/      # 布局组件
  │   ├── views/        # 页面
  │   ├── stores/       # 状态管理（Pinia，阶段 1+ 使用）
  │   ├── components/   # 公共组件
  │   └── utils/        # 工具函数
  ├── .env.development
  └── .env.production
  ```

- 配置 Element Plus 与全局样式基线。
- 封装全局 axios/fetch 请求模块：统一 baseURL、超时、错误提示、Token 预留拦截器。
- 配置路由：`/`（首页）、`/chat`（聊天）、`/upload`（文档上传）。
- 前端开发代理 `/api` 到后端本地端口。

### 5.5 基础页面框架（S0-05）

- 首页：项目名、入口导航（进入聊天、进入文档上传）。
- 聊天页：静态聊天容器 + 输入框 + 发送按钮占位，不接后端接口。
- 文档上传页：静态上传区域占位，不实现真实上传逻辑。
- 页面之间可路由跳转，布局统一（顶部导航或侧边栏，二选一后固定）。

### 5.6 配置与规范（S0-06）

- 后端 `.env.example` 包含：
  - `APP_ENV`（development/production）
  - PostgreSQL 连接配置
  - Qdrant 连接配置
  - LLM 配置预留：`LLM_PROVIDER`、`LLM_API_KEY`、`LLM_BASE_URL`、`LLM_MODEL`
  - 中转模式预留：`LLM_PROXY_BASE_URL`、`LLM_PROXY_API_KEY`
- 前端 `.env.development` / `.env.production` 配置 API 地址。
- 所有密钥只放本地 `.env`，提交到 git 的文件一律使用 `.env.example` 占位。
- 项目根目录 README：架构图（文本版）、目录说明、启动步骤。
- 根目录提供统一启动说明：`docker compose up -d` + 后端启动命令 + 前端启动命令。

### 5.7 学习解释文档（S0-07）

**硬性要求：阶段 0 的每个步骤完成后，必须同步产出一份详细解释文档。** 阅读对象是零基础学习者，目标是「看懂为什么这样做、背后的原理是什么」，而不是只记录命令结果。

- 文档统一存放：`docs/learning/阶段0/`，文件名与步骤一一对应，例如：

  ```text
  docs/learning/阶段0/
  ├── 01-FastAPI分层架构为什么这样拆.md
  ├── 02-Docker与PostgreSQL原理.md
  ├── 03-Qdrant向量库原理.md
  ├── 04-Vue3工程结构说明.md
  ├── 05-前后端如何联调.md
  └── 06-多环境配置与密钥安全.md
  ```

- 每篇文档必须包含以下小节：
  - **这一步做了什么**：一句话到一段话概括本步骤结果。
  - **为什么要这么做**：解释该步骤存在的原因、不做的后果。
  - **底层原理**：用类比 + 通俗语言讲清机制，例如：
    - 为什么项目要分层（路由/服务/适配/工具）
    - Docker 是什么、容器与镜像的区别
    - PostgreSQL 是什么、为什么用它存业务数据
    - Qdrant 是什么、向量库与传统数据库的区别
    - 环境变量为什么不能写死在代码里
    - 前后端为什么通过 HTTP/JSON 通信、`/api` 代理解决什么问题
  - **关键命令逐条解释**：每个命令的每个参数都说明含义。
  - **常见问题与避坑**：本步骤最容易出错的地方及解决办法。
- 文档语言：简体中文；允许用类比和画图（文本/ASCII 结构图），避免堆砌术语。
- 文档必须与实际代码同步：如果步骤代码有调整，对应文档须一并更新。
- 质量门槛：零基础读者按文档独立重跑一遍应能成功，卡住的地方视为文档不合格，需补充。

### 5.8 代码注释规范（S0-08）

**硬性要求：本项目所有代码（后端 + 前端）必须写清楚注释，阅读对象是零基础学习者。**

- **方法/函数**：每个方法必须有 docstring 或头部注释，说明：这个方法做什么、入参是什么、返回什么。
- **代码块/段落**：一段有独立逻辑的代码（如配置连接、异常处理、循环、条件分支）前必须有一行注释，说明这段代码做了什么、为什么这么做。
- **单行**：一行不直观、或初学者看不懂的代码（如魔法数字、复杂表达式、pydantic 字段含义）必须加行内注释。
- 注释语言：简体中文；解释「做什么 + 为什么」，不只写「设置变量」这类废话。
- 注释规范优先级高于精简原则：本项目以小白可读性为第一目标。
- 前端组件：`<template>` 的每个区块、`<script>` 的每个函数/响应式变量都要有注释。

示例（后端）：

```python
# 读取数据库连接串并创建连接池；pool_pre_ping 会在取出连接前先 ping，
# 避免拿到已失效的连接导致请求报错
engine = create_engine(settings.database_url, pool_pre_ping=True)
```

示例（前端）：

```ts
// 统一请求封装：所有接口都走这里，便于统一加 Token、超时和错误提示
const request = axios.create({ baseURL: '/api', timeout: 30000 })
```

## 8. 风险与避坑

| 风险 | 对策 |
|------|------|
| 端口冲突（5432/6333/5173 等） | 统一在配置中可改，启动前检查占用 |
| 密钥泄露 | 全部走 `.env`，提交文件只含占位符 |
| 依赖版本漂移 | requirements/pyproject 与 package.json 锁定版本 |
| 数据库/向量库容器数据丢失 | 挂载 named volume |
| 中转 Key 可用性 | 阶段 0 不实际调用模型，只预留配置，避免被黑盒服务绑架 |
| 前后端联调地址不一致 | 前端统一走 `/api` 代理，后端固定 CORS/端口配置 |
