# 07 · 多环境配置与密钥安全

## 这一步做了什么

补齐了项目的工程收尾：

- 根目录 `README.md`：项目简介、目录结构、启动步骤、端口一览、学习文档索引
- 后端 `backend/.gitignore`：忽略虚拟环境、缓存和 `.env`
- 汇总所有 `.env` 配置的用途与安全规则

## 为什么要这么做

### 1. 密钥不能写死在代码里

如果 API Key 直接写在代码里：

- 提交到 Git 后，全世界都能看到你的 Key
- 换 Key 要改代码重新发布
- 不小心发到公网 = 被别人盗用、扣费

正确做法：密钥放进本地 `.env`，代码只读环境变量。

### 2. 为什么有 `.env.example`

`.env` 是真实密钥，不能提交；`.env.example` 是「配置说明书」，可以提交。

别人克隆项目后：

```bash
Copy-Item .env.example .env
# 然后把自己的密钥填进去
```

### 3. 为什么区分多环境

开发和生产的数据库地址、密钥、日志级别都不同：

| 环境 | 用途 | 示例 |
|------|------|------|
| development | 本地开发 | 连 localhost 数据库、中转 Key |
| production | 线上运行 | 连线上数据库、官方 Key |

同一份代码通过环境变量切换配置，不需要改代码。

## 底层原理

### 环境变量怎么工作

后端启动时，`pydantic-settings` 读取 `.env` 文件，把里面的键值映射到 `Settings` 类的字段：

```dotenv
DATABASE_URL=postgresql+psycopg://aigc_user:xxx@localhost:5433/aigc_chat
```

```python
class Settings(BaseSettings):
    database_url: str = "..."  # 自动被 .env 覆盖
```

### .gitignore 怎么工作

`.gitignore` 告诉 Git「这些文件不提交」：

```gitignore
.env
venv/
__pycache__/
```

`git status` 检查文件时直接忽略它们，防止密钥和环境误入库。

### 阶段 2 的加密预留

数据库里存 AI 模型的 API Key 时，不能明文存。本项目已在依赖里预装 `cryptography`，阶段 2 会用加密算法把 Key 加密后再写库，读取时解密。

## 关键文件逐条解释

| 文件 | 作用 |
|------|------|
| 根目录 `.env` | 数据库、Qdrant、LLM 全部配置（本地真实值，不入库） |
| `backend/.env` | 后端运行时读取的配置（密码与根级一致） |
| `backend/.env.example` | 配置模板，提交到 Git |
| `backend/.gitignore` | 忽略 venv、缓存、.env |
| `frontend/.env.development` | 前端开发环境变量（非密钥，可提交） |
| `README.md` | 新人启动指南 |

## 常见问题与避坑

1. **改了 `.env` 不生效**：后端要重启，前端要重启 `pnpm dev`。
2. **密码不一致连不上**：根级 `.env` 和 `backend/.env` 的 PostgreSQL 密码/端口必须一致。
3. **误提交密钥**：立即改 Key，并在 `.gitignore` 补上对应文件；历史提交里的密钥视为已泄露。
4. **`.env.example` 也要真实值吗**：不需要，填占位符 `change_me` 即可。
