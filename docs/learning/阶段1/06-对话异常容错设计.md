# 06 · 对话异常容错设计

## 这一步做了什么

完善了对话链路的异常容错：

- 适配层把底层异常统一映射为 `ModelError(code, message)`
- SSE 接口捕获 `ModelError`，转成 `error` 事件（不中断连接、不返回 500）
- 前端收到 `error` 事件后停止流，把 AI 消息改为友好提示
- 真实调用智谱 GLM-4-Flash 联调通过：逐段 `delta` → `done`

## 为什么要这么做

AI 调用比普通接口更容易失败：

- Key 过期、额度不足
- 网络超时、中转商断流
- 模型名写错、厂商临时故障

如果这些错误直接返回 500 或抛堆栈，前端会白屏/卡死，用户不知道发生了什么。容错的目标：**任何故障都有明确的、用户能看懂的提示，且程序不崩**。

## 底层原理

### 异常统一映射

底层异常千奇百怪，先翻译成 5 种标准 `code`：

| code | 触发特征 | 用户提示 |
|------|----------|----------|
| `invalid_key` | 401 / auth / 未配置 Key | API Key 无效，请检查配置 |
| `insufficient_quota` | 429 / quota | 账户额度不足 |
| `timeout` | httpx.TimeoutException | 响应超时 |
| `stream_broken` | 流/连接异常 | 连接中断 |
| `unknown` | 其他 | 服务器内部错误 |

```python
def _map_error(exc):
    text = str(exc).lower()
    if "auth" in text or "401" in text:
        return ModelError("invalid_key", "API Key 无效")
    ...
```

### SSE 层的错误事件

```python
except ModelError as exc:
    yield sse({"type": "error", "code": exc.code, "message": exc.message})
```

流式接口已经开始后不能返回 JSON 错误页，所以错误也走 SSE：前端 `onError` 处理。

### 前端兜底

```ts
catch {
  aiMsg.content = '[错误] 网络异常，请稍后重试'
}
```

即使 fetch 本身失败（后端没启动、断网），前端也要恢复输入框并提示，不能一直 loading。

### 关键经验：真实联调暴露 mock 覆盖不到的问题

单元测试用 mock 通过，但真实调用发现两个坑：

1. LiteLLM 流式返回需要 `await` 后才能迭代
2. 智谱模型名必须加 `openai/` 前缀才能被 LiteLLM 识别

所以**真实联调是验收的一部分**，mock 只保证逻辑正确，不能保证厂商兼容。

## 关键命令逐条解释

| 命令 | 含义 |
|------|------|
| `pytest -q` | 全量后端测试 |
| `curl -N -X POST .../api/chat/stream ...` | 真实流式联调，`-N` 禁止缓冲 |
| `pnpm build` | 前端类型检查 + 打包 |

## 常见问题与避坑

1. **错误变成 `unknown`**：说明异常没被 `_map_error` 识别，查看完整异常文本补充映射规则。
2. **前端一直 loading**：`onDone`/`onError` 必须都要 `loading=false`，漏一个就卡死。
3. **mock 与真实行为不一致**：涉及厂商 SDK 的 mock 要按真实返回结构写，联调阶段重点验证。
4. **Key 换了不生效**：重启后端；前端模型下拉选的模型也要在清单里。
