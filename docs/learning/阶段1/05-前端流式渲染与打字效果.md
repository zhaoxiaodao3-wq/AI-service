# 05 · 前端流式渲染与打字效果

## 这一步做了什么

把聊天页改造成「豆包风格」并接入真实流式对话：

- 左侧菜单：新会话按钮 + 历史会话列表（内存态，阶段 2 持久化）
- 右侧聊天区：消息列表 + 输入区
- 输入区支持上传文件/图片（附件条展示，随消息携带）
- 模型下拉：从 `GET /api/models` 拉取
- `chatStream.ts`：用 fetch 读取 SSE，逐段追加 AI 回复，实现打字效果

## 为什么要这么做

### 1. 为什么抄豆包的布局

豆包式布局（左会话 + 右聊天）是主流 AI 对话产品的通用形态：

- 左侧：管理「多个会话」，用户可以开新会话、回看历史
- 右侧：专注当前对话，信息层级清晰

这种布局也是后续多会话管理的天然结构，阶段 2 只需把内存会话换成数据库接口。

### 2. 为什么用 fetch 而不是 EventSource

浏览器原生 `EventSource` 只能发 GET 请求。我们的对话接口要 POST 消息体，所以用 `fetch` + `response.body.getReader()` 手动读流。

### 3. 为什么先占位再追加

发送后立刻插入一条空的 AI 消息，`onDelta` 把增量不断追加进去。这样 UI 从第一个字开始就在更新，而不是等全部完成后一次性渲染。

## 底层原理

### ReadableStream 读流

```ts
const reader = resp.body.getReader()
const { done, value } = await reader.read()
```

`getReader()` 拿到可读流；每 `read()` 一次取一个二进制块。块可能很小（几个字符），也可能跨多个事件，所以要累积到 buffer 再按 `\n\n` 切分。

### 缓冲区为什么必要

```ts
buffer += decoder.decode(value, { stream: true })
const parts = buffer.split('\n\n')
buffer = parts.pop() ?? ''
```

一次网络分块可能只包含半个事件。把不完整的尾部留在 buffer，下次续上再解析，避免事件被截断。

### 内存会话模型

```ts
sessions = [{ id, title, messages }]
activeSessionId = 1
```

切换会话 = 改 `activeSessionId`，页面显示对应 `messages`。阶段 2 把这个结构换成「数据库会话 + 接口拉取」。

### 附件为什么阶段 1 只展示

文件理解需要完整的解析链路（阶段 3 文档、后续多模态模型）。阶段 1 先把「上传、展示、随消息携带」做通，模型只收到文本；附件字段后端原样透传不报错，为阶段 3 留好接口形状。

## 常见问题与避坑

1. **打字效果不出来**：检查浏览器 Network 是否收到多条 `data:` 事件，以及后端是否真的逐段 yield。
2. **附件不显示**：图片用 `URL.createObjectURL` 生成预览，对象 URL 只在当前页面有效。
3. **切换会话后消息错乱**：所有读写都要基于 `activeSession`，不要直接操作全局数组以外的副本。
4. **Enter 发送与换行冲突**：用 `@keydown.enter.exact` 让 Enter 发送，Shift+Enter 换行。
