# 01 · 模型响应缓存（把模型回答"存起来"，重复问题秒回）

## 这一步做了什么

给聊天加了一个**回答缓存**：同一个问题第一次问的时候，把模型的回答存进 Redis；第二次再问完全相同的问题，就不调模型了，直接把存好的回答原样返回。

```text
你第一次问：AI 是什么？
  → 没有缓存 → 花钱调用模型 → 回答存进 Redis
你第二次问：AI 是什么？
  → 有缓存 → 直接返回存好的回答（不调用模型）
```

## 为什么要这么做（用食堂打比方）

模型调用有两大代价：**花钱**（按 token 计费）和**花时间**（生成几十上百字需要几秒）。

可以想象一家食堂：每个菜都是客人点了以后现炒（调用模型），又慢又费煤气（成本和延迟）。如果热门菜提前做好放在保温柜里（Redis），客人点到直接端出来，又快又省钱。

聊天里有很多"热点问题"是大家反复问的（比如"怎么改密码""RAG 是什么"），缓存能省掉大量重复的模型调用。

## 底层原理

### 1. 缓存的"钥匙"（key）长什么样

缓存必须能区分"哪些问题算同一个"。我们的方案是：

```text
key = chat:{模型名}:{sha256(问题原文)}
```

- `chat:` 前缀：方便在 Redis 里统一识别、清理（类似给文件归类命名）。
- `{模型名}`：同一个问题，用不同模型回答不一样，必须分开存，否则会张冠李戴。
- `{sha256(问题原文)}`：把问题原文做一次哈希（一种"内容指纹"计算），变成一串固定长度的乱码。**相同内容哈希值一定相同，内容差一个字哈希值完全不同**，所以它能精确判断"两个问题是否一字不差"。

> 为什么不用问题原文直接当 key？因为原文可能很长，Redis 的 key 越长越浪费内存；哈希后固定 64 个字符，长短问题都一样，而且不会包含特殊字符。

### 2. 命中与未命中（读缓存 → 没读到 → 调模型 → 写缓存）

```text
收到问题
  ├─ 算 key → GET key
  │    ├─ 命中（Redis 里有）→ 直接把回答作为 delta 事件返回，结束
  │    └─ 未命中 → 调模型 → 拿到回答 → SET key 回答（TTL 1 小时）→ 返回
```

代码在 `backend/app/services/chat_service.py` 的 `stream_chat_events` 里：

```python
if s.cache_enabled and not use_rag and not use_tools and question:
    cache_key = f"chat:{selected}:" + hashlib.sha256(question.encode("utf-8")).hexdigest()
    cached = cache_service.get_cache(cache_key)
    if cached is not None:
        yield {"type": "delta", "content": cached}
        yield {"type": "done", "usage": None, "citations": None}
        return   # 命中缓存：不调模型，直接结束
```

### 3. Redis 读写封装（backend/app/services/cache.py）

缓存代码只有两个函数，全部包了 `try/except`：

```python
def get_cache(key):
    try:
        with redis_client() as client:
            return client.get(key)
    except Exception:
        return None          # Redis 挂了？当成"没缓存"，照常调模型

def set_cache(key, value, ttl=None):
    try:
        with redis_client() as client:
            client.set(key, value, ex=ttl or get_settings().response_cache_ttl_seconds)
    except Exception:
        pass                 # 写缓存失败不影响聊天，静默忽略
```

**重点**：Redis 只是"加速器"，不是"必需品"。Redis 出故障时，缓存层静默降级——聊天依然正常，只是每次都调模型而已。这就是"缓存不能成为单点故障"的工程原则。

### 4. 哪些请求不缓存（RAG / 工具）

代码里明确排除了两种情况：

```python
if s.cache_enabled and not use_rag and not use_tools and question:
```

- **RAG 请求不缓存**：RAG 的回答依赖检索到的知识库内容。知识库更新后，同一问题答案应该跟着变；缓存会让用户拿到旧答案。
- **工具请求不缓存**：工具调用（查天气、查汇率）结果是实时变化的，缓存会返回过期数据。

只有纯模型对话才缓存——这正好是"答案稳定、请求高频"的场景。

### 5. 配置项（backend/app/core/config.py）

| 配置项 | 默认值 | 含义 |
|--------|--------|------|
| `cache_enabled` | `True` | 总开关 |
| `response_cache_ttl_seconds` | `3600` | 缓存存活时间，默认 1 小时 |

TTL（Time To Live，存活时间）：Redis 里每个 key 可以设"到期自动删除"。1 小时后旧答案自动作废，模型会重新回答，避免信息过时。

## 常见问题与避坑

1. **缓存 key 忘带模型名** → 不同模型的回答会互相覆盖，出现"回答串台"。所以 key 里必须带 `{模型名}`。
2. **TTL 设太短**（比如 1 分钟）→ 缓存形同虚设，热点问题还是频繁调模型；**设太长** → 信息过期，用户拿到旧答案。1 小时是常见折中。
3. **缓存了 RAG / 工具请求** → 上下文错乱：知识库更新了但答案不变、天气永远是第一次查的。务必按上面代码那样排除。
4. **Redis 挂了聊天就挂** → 说明没做降级。我们的 `get_cache`/`set_cache` 全部 try/except，Redis 故障时自动跳过缓存，保证聊天可用。
5. **key 大小写/空格敏感**："AI 是什么"和"ai 是什么"哈希不同，不会命中同一个缓存。这是精确缓存，不是语义缓存（语义缓存需要向量相似度，属于更高级的方案）。

## 小结

一句话记住：**缓存 = 用"内容指纹"当钥匙，把模型回答存进 Redis，命中就秒回，RAG/工具不缓存，Redis 挂了不阻塞聊天。**
