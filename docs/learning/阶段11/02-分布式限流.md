# 02 · 分布式限流（防止有人把你的服务打爆）

## 这一步做了什么

给聊天接口加了一层"门禁"：限制单位时间内的请求次数。

- **按 IP 限流**：同一个 IP 默认最多 30 次/分钟
- **按用户限流**：登录用户默认最多 60 次/分钟（有 token 按用户算，更宽松）
- **分布式**：计数存在 Redis 里，所有后端实例共享同一个计数器
- **自动降级**：Redis 出故障时，自动退回单机内存计数，服务不挂

超限的请求返回 HTTP 429：

```json
{"code": 429, "message": "请求过于频繁，请稍后再试"}
```

## 为什么要这么做（用餐厅限号打比方）

如果不限流，会发生什么？

- **被刷爆**：脚本批量调用聊天接口，每个请求都花钱调模型，账单几小时爆表。
- **被打挂**：瞬间几千个并发请求，数据库、模型网关全被压垮，正常用户也访问不了。
- **被薅羊毛**：接口被当作免费模型代理滥用。

限流就像餐厅的"限号就餐"：同一桌（IP/用户）短时间内不能连续点太多菜，既保证服务质量，也防止有人把后厨（模型服务）累垮。

## 底层原理

### 1. 滑动窗口 vs 固定窗口（为什么用滑动窗口）

| 方案 | 做法 | 问题 |
|------|------|------|
| 固定窗口 | 每 1 分钟开一个新窗口，窗口内计数 | 窗口边界处会"漏"：59 秒发了 30 次，下一秒又能发 30 次 |
| 滑动窗口 | 只看"过去 60 秒内"有多少次 | 边界问题消失，但实现更复杂 |

我们用的是**滑动窗口**：任意时刻，往前数 60 秒内的请求次数超过上限就拒绝。

### 2. 用 Redis 的 ZSET 实现滑动窗口

ZSET（有序集合）是 Redis 的一种数据结构，每个元素带一个分数（score），可以按分数排序、按分数范围删除。

我们把"每次请求"作为集合的一个成员，分数 = 请求时刻的时间戳：

```text
key = rl:ip:192.168.1.5        （按 IP）或 rl:user:7 （按用户）
成员 = 随机 UUID
分数 = 当前时间戳（秒）
```

判断"60 秒内是否超限"只需 4 步（代码里用 Redis pipeline 一次性执行）：

```text
① ZADD   把本次请求写进集合，score=now
② ZREMRANGEBYSCORE  删除 score < now-60 的旧记录（把窗口外的清掉）
③ ZCARD  数一下集合还剩多少个成员 = 过去 60 秒的请求数
④ EXPIRE 给 key 设 120 秒过期（防止长期没人访问时 key 越积越多）
```

最后判断：`count <= limit` 就放行，否则 429。

对应代码 `backend/app/core/rate_limit.py`：

```python
pipeline = client.pipeline()
pipeline.zadd(key, {member: now})                    # ① 记录本次请求
pipeline.zremrangebyscore(key, 0, now - window)      # ② 清掉窗口外的
pipeline.zcard(key)                                  # ③ 数剩余次数
pipeline.expire(key, window * 2)                     # ④ 设置过期
_added, _removed, count, _expired = pipeline.execute()
return int(count) <= limit
```

### 3. 为什么叫"分布式"限流

单机限流是"每台服务器各数各的"：部署 3 个后端实例，每个都允许 30 次/分钟，那同一个用户实际上能打 90 次。

把计数器放进 **Redis** 后，所有实例读写的是**同一个计数器**，总数才真正被限制住——这就是"分布式"的含义：限制逻辑分布在各实例上，但计数是全局共享的。

### 4. Redis 挂了怎么办（降级到内存）

限流绝不能成为"把服务打挂的那根稻草"。代码里 `try` 整个 Redis 流程，一旦异常就退到内存版：

```python
try:
    ...  # Redis 滑动窗口
except Exception:
    async with self.lock:
        cutoff = time.monotonic() - window
        self.hits[key] = [t for t in self.hits[key] if t > cutoff]  # 内存里清窗口
        if len(self.hits[key]) >= limit:
            return False
        self.hits[key].append(time.monotonic())
        return True
```

内存版是"每实例各自计数"（退化了），但至少接口不会被 Redis 故障连累——**可用性优先于精确性**。

### 5. 怎么区分 IP 和用户（中间件的识别逻辑）

`RateLimitMiddleware` 是 FastAPI 的中间件，每次请求先经过它：

```python
if scope["type"] != "http" or scope.get("path") != "/api/chat/stream":
    await self.app(scope, receive, send)   # 非聊天接口直接放行
    return

client = scope.get("client")
key = client[0] if client else "unknown"   # 默认按 IP
limit = self.limit
for header in scope.get("headers", []):
    if header[0] == b"authorization" and header[1].startswith(b"Bearer "):
        payload = decode_access_token(header[1][7:].decode("utf-8"))
        if payload:
            key = f"user:{payload.get('sub')}"   # 有合法 token 就按用户算
            limit = self.user_limit
        break
```

逻辑要点：

- **只对 `/api/chat/stream` 限流**：聊天接口最贵（调模型），其他接口不动，避免误伤。
- **默认按 IP**：没登录（或 token 无效）就按 IP 算。
- **有效 token 按用户算**：`user:{用户ID}` 作为 key，登录用户享更高额度（60 次/分），因为正常用户不该被自己打爆。

### 6. 配置项（backend/app/core/config.py）

| 配置项 | 默认值 | 含义 |
|--------|--------|------|
| `rate_limit_per_minute` | `30` | 匿名 IP 每分钟次数 |
| `rate_limit_user_per_minute` | `60` | 登录用户每分钟次数 |


## 常见问题与避坑

1. **用户维度要先解 Token**：顺序不能反——必须先 `decode_access_token` 成功才用用户 key；token 无效就退回 IP 维度，否则任何人都能伪造 key 绕过限流。
2. **Redis 挂了不能把接口打挂**：限流是"保护伞"不是"定时炸弹"，异常必须降级而不是抛 500。
3. **ZSET 会膨胀**：每个请求一个成员，如果 key 不过期会无限增长。`expire(key, window*2)` 保证 2 分钟内没人访问的 key 自动消失。
4. **只限聊天接口**：全局限流会误伤文件上传、登录等正常接口；按路径精准限流才合理。
5. **429 要让用户看得懂**：返回统一格式 `{"code":429,"message":"请求过于频繁，请稍后再试"}`，前端可以据此提示而不是当成系统错误。

## 小结

一句话记住：**限流 = 用 Redis ZSET 做滑动窗口（4 步：写入→清窗口→计数→过期），IP 30 次/分、用户 60 次/分，Redis 挂了自动降级内存，超限返回 429。**
