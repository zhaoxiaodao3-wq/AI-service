# 02 · 限流与流式重试

## 做了什么

新增两项容错能力：

- **聊天接口限流**：`RateLimitMiddleware` 按客户端 IP 滑动窗口计数，默认 30 次/分钟，超限返回 HTTP 429。
- **流式重试**：`stream_chat` 在未输出任何 `delta` 时自动重试，默认 `LLM_RETRY_COUNT=1`；一旦输出过内容就不再重试，避免重复。

## 为什么

聊天接口调用大模型，是成本最高、最容易被打爆的入口。限流防止被刷；重试解决网络抖动/中转断流导致的“第一段都没出来”问题。

## 原理

### 滑动窗口

```text
每次请求：记录当前时间
过滤 60 秒前的记录
数量 >= 30 → 429
否则追加记录
```

### 流式重试

```text
尝试1：acompletion 建立连接 → 逐段 yield
  ├─ 还没 yield 就断 → 重试
  └─ 已经 yield 过 delta → 直接抛错，不重试
```

## 命令解释

```powershell
for ($i=0; $i -lt 31; $i++) { try { Invoke-WebRequest -Uri http://localhost:8000/api/chat/stream -Method Post -ContentType "application/json" -Body '{"messages":[{"role":"user","content":"hi"}],"model":"glm-4-flash"}' -UseBasicParsing | Out-Null } catch { Write-Output $_.Exception.Response.StatusCode.value__; break } }
```

压测限流，应能看到 429。

## 避坑

- 限流只作用于 `/api/chat/stream`，文件上传等其他接口不受影响。
- 重试次数别设太大，否则故障时会让模型计费翻倍。
- 重试只解决“没内容就断”，不能解决“内容中途断开”，后者应提示用户重发。
