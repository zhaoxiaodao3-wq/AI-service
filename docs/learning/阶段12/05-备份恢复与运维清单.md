# 05 · 备份恢复与运维清单（数据是命，定期备份是底线）

## 这一步做了什么

交付两套运维脚本 + 一份运维清单：

- `scripts/backup.sh`：PostgreSQL 全量备份 → gzip 压缩 → 按日期命名 → 自动清理只留最近 7 份
- `scripts/restore.sh`：把备份文件恢复到数据库（先清空再导入，防止残留冲突）
- 推荐挂在宝塔"计划任务"里每天自动执行
- 运维清单：日志、观测、更新、扩容、故障排查的日常 checklist

## 为什么要这么做（用"存钱"打比方）

服务器上的数据库就像你的积蓄——**平时感觉不到它多重要，丢了才知道天塌了**。

会丢数据的场景：

- 手滑执行了危险 SQL
- 服务器硬盘损坏 / 被勒索病毒加密
- 云厂商机房故障（小概率但存在）
- 自己改迁移脚本把表搞坏了

备份就是**定期往另一个抽屉里存一份"钱"**：真出事了，从抽屉里拿出来恢复，损失最多一天的数据，而不是一切归零。

## 底层原理

### 1. backup.sh 逐段拆解（scripts/backup.sh）

```bash
# 1) 在宿主机建备份目录
mkdir -p "$BACKUP_DIR"                        # 默认 /opt/aigc-backups

# 2) 通过容器执行 pg_dump，把数据库导出成 SQL
docker exec -e PGPASSWORD="$POSTGRES_PASSWORD" "$POSTGRES_CONTAINER" \
  pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" --no-owner --no-privileges \
  | gzip > "$OUT_FILE"                        # 压缩后写到宿主机
```

关键点：

- **`docker exec` 进容器跑 pg_dump**：备份程序不需要装在宿主机，复用 postgres 镜像里的工具，版本永远匹配。
- **`--no-owner --no-privileges`**：备份文件里不记录"属主用户"，换环境恢复不会因为用户不存在而失败。
- **`gzip` 压缩**：SQL 文本压缩率很高（通常 10 倍以上），省磁盘。
- **`$OUT_FILE = aigc_20260820_030000.sql.gz`**：文件名带时间戳，一眼看出是哪天的备份。

```bash
# 3) 只保留最近 KEEP_N 份，删更早的
ls -1t "$BACKUP_DIR"/aigc_*.sql.gz | tail -n +$((KEEP_N + 1)) | while read -r old; do
  rm -f "$old"
done
```

`ls -1t` 按时间倒序 → `tail -n +8` 跳过前 7 个 → 剩下的都是最老的 → 删除。这样备份目录**永远只占"最近 7 份"的空间**，不会无限膨胀。

### 2. restore.sh 逐段拆解（scripts/restore.sh）

```bash
# 1) 清空旧数据（先删 schema 再重建，比 DROP TABLE 干净彻底）
docker exec -e PGPASSWORD=... psql -U ... -d ... \
  -c "DROP SCHEMA public CASCADE; CREATE SCHEMA public;"

# 2) 解压备份文件导入
gunzip -c "$BACKUP_FILE" | docker exec -i -e PGPASSWORD=... psql -U ... -d ...
```

恢复后**重启 backend/worker**，让 Alembic 自动把表结构对齐到迁移版本（备份恢复的是数据，结构以迁移为准）。

### 3. 宝塔计划任务挂 cron

```text
宝塔面板 → 计划任务 → 添加任务：
  任务类型：Shell 脚本
  任务名称：aigc 数据库备份
  执行周期：每天 03:00
  脚本内容：bash /www/wwwroot/aigc/scripts/backup.sh
  执行结果：钩上"失败时通知我"（可选）
```

## 你要做的操作步骤

### 第 1 步：首次手动备份验证（先证明脚本能跑）

```bash
cd /www/wwwroot/aigc
bash scripts/backup.sh
# 期望输出：
#   [backup] 开始备份 aigc -> /opt/aigc-backups/aigc_20260820_030000.sql.gz
#   [backup] 完成: 1.2M
#   [backup] 当前备份列表: ...
```

### 第 2 步：挂每天自动备份

```text
宝塔面板 → 计划任务 → 添加任务（如上，每天 03:00 跑 backup.sh）
```

### 第 3 步：验证恢复流程（重要，别等出事了才学）

```bash
# 1) 看有哪些备份
ls -lht /opt/aigc-backups

# 2) 演练恢复（选一个备份文件）
bash scripts/restore.sh /opt/aigc-backups/aigc_20260820_030000.sql.gz

# 3) 重启后端让 Alembic 对齐结构
docker compose -f docker-compose.prod.yml restart backend worker

# 4) 验证数据回来了
curl http://127.0.0.1:8000/api/health
# 登录网页确认账号/会话/文档还在
```

### 第 4 步：备份文件再复制一份到别处（防服务器整台挂掉）

```text
方案 A（推荐，最简单）：宝塔面板 → 文件 → /opt/aigc-backups → 右键 → 下载到本地
方案 B：阿里云 OSS 定时同步（宝塔有"阿里云OSS"插件，把备份目录同步上去）
```

**备份存在同一台服务器上，服务器整台损坏时备份也一起没了**——所以重要数据务必有一份"异地"副本（下载到本地或传 OSS）。

## 日常运维清单（贴墙上）

### 每天

- [ ] 检查宝塔计划任务日志：备份任务是否执行成功（红字=失败，立刻处理）

### 每周

- [ ] 登录 Grafana（http://服务器IP:3000 或经反代）看：
  - Explore → Loki：`{container="aigc-backend"}` 有无 ERROR 日志
  - Explore → Tempo：抽查一条聊天请求的 Trace，各环节耗时是否正常
- [ ] 看 Docker 磁盘占用：`docker system df`，清理悬空镜像 `docker image prune`

### 每次发版

- [ ] 先备份（`bash scripts/backup.sh`）
- [ ] `docker compose -f docker-compose.prod.yml pull && up -d`
- [ ] 验证健康检查 + 浏览器实测注册/登录/聊天/上传
- [ ] 数据库结构有变时确认迁移自动执行（后端日志出现 `alembic upgrade head 完成`）

### 故障排查速查表

| 症状 | 先查什么 |
|------|----------|
| 页面打不开 | 安全组 80/443 是否放行；宝塔网站是否正常运行；`docker compose ps` 容器状态 |
| 聊天报错 | 后端日志 `docker logs aigc-backend --tail 50`；Tempo 看 Trace 哪一环报错 |
| 上传文档一直处理中 | worker 容器是否活着（`docker logs aigc-worker --tail 50`） |
| 数据库连不上 | `docker logs aigc-postgres --tail 50`；.env.prod 密码是否与 compose 一致 |
| 磁盘快满了 | `df -h`；`docker system df`；清理旧备份 `ls /opt/aigc-backups` |

### 资源限制速查（docker-compose.prod.yml 已内置）

| 服务 | CPU | 内存 |
|------|-----|------|
| postgres | 1.0 | 512M |
| qdrant | 1.0 | 1G |
| redis | 0.5 | 256M |
| backend | 1.5 | 1G |
| worker | 1.0 | 1G |
| frontend | 0.5 | 256M |

按需调整：内存紧张先减 qdrant/worker；要跑大模型服务再加 backend。

## 常见问题与避坑

1. **备份在容器里 vs 宿主机**：备份文件写在**宿主机**（/opt/aigc-backups），容器删了备份还在。别把备份写进容器卷里（容器删了卷还在但难迁移）。
2. **恢复是"覆盖"操作**：restore 先清空再导入，执行前确认备份文件是对的、是你要恢复的时刻。
3. **只备份 PG 不够**：Qdrant 向量数据也在生产里（知识库/记忆）。简单方案：Qdrant 卷（qdrant_data）用宝塔"整目录备份"定期打包；或接受"重新上传文档重建知识库"。本阶段 PG 优先，Qdrant 备份列为可选增强。
4. **时区**：备份文件名时间戳是服务器本地时区，跨时区看文件名别懵。
5. **cron 环境变量**：backup.sh 的 `POSTGRES_PASSWORD` 依赖 .env.prod 传入——宝塔计划任务执行时不会自动加载 .env.prod，建议把变量写进脚本顶部（脚本里已留 `${POSTGRES_PASSWORD:-}` 占位），或在计划任务命令前 `export $(cat .env.prod | xargs)`。

## 小结

一句话记住：**备份 = pg_dump + gzip 定时跑，只留最近 7 份，异地再存一份；恢复 = 清库 + 导入 + 重启对齐迁移；运维 = 天天看备份、周周看观测、发版前先备份。**
